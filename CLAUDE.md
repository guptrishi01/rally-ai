# CLAUDE.md

Project-specific context for Rally AI. See [README.md](README.md) for the product overview and [docs/stat-definitions.md](docs/stat-definitions.md) for stat calculations.

## Data capture: SwingVision

Match and practice footage is recorded with the [SwingVision](https://swing.vision/) app via a phone fence mount, not logged manually from scratch. Its AI auto-tracks serves, shot placement, and speed at the shot level even without a paid subscription; it's the *point/game/set rollup* specifically that requires SwingVision Pro — confirmed by inspecting two real exports (see below), not assumed.

**Consent:** verbal consent from the other player is required before recording any rally practice or match, since the camera captures both sides of the court.

**Manual review is required before trusting SwingVision-derived data — do not treat any auto-tag as ground truth, regardless of which path produced it:**

- **Winner / unforced error / forced error classification** — unreliable from *either* source that can produce it: SwingVision's own Pro-tier auto-tag (this is why the app has an "Edit Point" correction feature), or `reconstruct.py`'s own shot-geometry heuristic (see below). Every point either path produces gets `needs_review=True` — no exceptions, not even the categories that look unambiguous.
- **Net approach outcomes (NA / NPW / NS%)** — SwingVision has no dedicated column for this at all, at any tier. `reconstruct.py` makes an educated guess (a `Volley`/`Overhead` stroke by the tracked player) but it's still just a guess subject to the same review gate — not treated as more trustworthy than a blank field waiting on manual tagging.
- Everything else in `stat-definitions.md` (serve in/out, aces, double faults, service/return games, break points, deuce points, rally/shot data) maps cleanly to SwingVision's automatic tracking *when a Pro export's Points sheet is actually populated*, and doesn't need manual re-verification beyond spot checks in that case.
- Energy Rating, Mental Rating, and pros/cons are self-assessment by design — always manual, unrelated to SwingVision.

There is no dedicated wall/backboard session mode in SwingVision (only Match, Rally, Service Practice, Ball Machine Mode for tennis). Wall-practice tracking is unverified — don't assume its stats are trustworthy without checking against a manual count first.

## Database schema

`data/schema.sql` defines the `match` / `set` / `point` tables (SQLite). No new columns were added for SwingVision's review-flag tracking; that lives entirely in the pre-SQL JSON staging step described below, not in the database. `import_notes`/`shot_pattern_summary` (informational data-quality findings and coaching-context enrichment, both described below) live the same way — in the staged JSON only, never as new database columns.

**3NF pass on `point`:** `net_point_won` was dropped — it was always exactly equal to `point_won` whenever `net_approach` was true (pure redundant storage, confirmed against its own docstring and `docs/stat-definitions.md`'s NPW formula), so a net approach's own success is now always just `net_approach = TRUE AND point_won = TRUE` at query time, never a stored column. `point_end_type` also functionally determines `point_won` for all 7 values (e.g. `'ace'` always means `point_won=TRUE`), but `point_won` stays a separate stored column on purpose — it's independently reviewable during manual review, matching the "no single auto-tag is trusted alone" philosophy the whole SwingVision pipeline is built around. A `CHECK` constraint on `point` enforces the two never silently disagree instead.

## SwingVision import pipeline

`src/swingvision_import/` turns a SwingVision `.xlsx` export into rows in `data/schema.sql`, in deliberately separate steps — never straight to SQL in one call:

1. **`pipeline.ingest(xlsx_path, ...)`** — parses the export and writes a staging JSON file to `src/swingvision_import/pending/` (gitignored — personal match data, not code). Never touches SQL.
2. *(Optional, opt-in)* **`pipeline.suggest(client, json_path)`** — Claude-assisted suggestions for flagged points, described below.
3. **`pipeline.finalize(json_path)`** — loads that JSON and writes the match + its sets + all its points into SQLite in one atomic transaction.

**The hard rule finalize() enforces:** a match is not written to SQL — at all, not partially — while any `PointRecord.needs_review` flag is still `True`. `load.finalize_and_load` raises `UnresolvedReviewError` and writes nothing if so. Resolve flags by hand-editing the pending JSON before calling `finalize()` again. This is the concrete implementation of the "manual review is required" rule above — code enforces it, not just documentation.

**The real export structure is now confirmed** (against two real, non-Pro exports — no longer a guess): six sheets exist — `Settings, Shots, Points, Games, Sets, Stats`. **`Points`/`Games`/`Stats` are empty without SwingVision Pro; `Sets` (final scores) and `Shots` (full per-shot AI tracking — player, stroke, speed, in/out/net result, grouped by a match-wide `Point` counter) are populated regardless of tier.** `config.DEFAULT_COLUMN_ALIASES` reflects the real confirmed headers now, not secondhand-reporting guesses — the one remaining unverified piece is the *value vocabulary* inside `Points`' `Serve State`/`Detail` columns, since no Pro export has been seen with actual data rows to check against.

**Two parse paths, chosen automatically by `pipeline.ingest()`:**

- **Direct parse** (`transform.py`) — used when `Points` has real rows (Pro). SwingVision's own point classification flows through, with `winner`/`unforced_error`/`forced_error` flagged per `config.NEEDS_REVIEW_END_TYPES`, same as before.
- **Shots-based reconstruction** (`reconstruct.py`) — the fallback when `Points` is empty, which is what actually ran for both real exports available so far (Pro not required at all for a usable import). Groups `Shots` rows by point, derives `is_serving`/serve-in/point-winner/a coarse `point_end_type` bucket/`net_approach` from the shot sequence, then forward-simulates standard ad-scoring tennis rules (`assign_game_set_boundaries`) to assign `game_number`/`set_number`/`is_tiebreak_game` — SwingVision's own `Game`/`Set` columns on `Shots` are always `0` and unusable. **Two kinds of point numbers get excluded, deliberately distinguished:** a **gap** (zero shots at all — a recording dropout, confirmed real: ~15-40 per half in the two files tested) is skipped and logged, never fabricated; an **excluded non-match point** (shots exist, but none of them is a real rally-type `Type` — e.g. a `Stroke=="Feed"` ball sent across between points, confirmed real in both files) is also excluded, but reported separately since it isn't a data gap, it's correctly-tracked non-rally activity that would otherwise silently corrupt game/set boundary counting if treated as a real point. **Every point this path produces gets `needs_review=True`, unconditionally** — stricter than the direct-parse path, because this is a heuristic *we* invented from raw shot geometry, not even SwingVision's own (already-distrusted) classifier. One confirmed real ambiguity that's exactly why: a `second_serve` shot marked `Result='Out'` (a fault) was seen immediately followed by a `second_return` shot in the same point, which shouldn't happen if the serve genuinely faulted.

**Claude-assisted suggestions, never auto-resolution** (`review_assist.py`, invoked via `pipeline.suggest()`): for each reconstructed point (identified by `PointRecord.source_point_number`, which traces back to its original `Shots` rows), one Claude call reasons over that point's actual shot sequence (stroke/speed/direction/result — structured data, no video/vision involved) and suggests a refined `point_end_type`, attached to `ai_suggested_point_end_type`/`ai_suggestion_reasoning`. **This never clears `needs_review`** — per the user's explicit rule, a Claude suggestion is one more thing for the human to confirm, not a second silent auto-tagger stacked on top of the first. `unresolved_flags()` surfaces the suggestion (and its reasoning) alongside the original flag so the reviewer sees both. Opt-in and separate from `ingest()` on purpose, since it spends real API money. Reuses `ai.client`'s `AnthropicClientLike` Protocol and injected-client pattern rather than reinventing it — same "tests never touch the real API" guarantee. The real client itself is constructed exactly once, in `scripts/client.py` (loads `ANTHROPIC_API_KEY` from a gitignored `.env` via `python-dotenv`) — never inside `ai/` or `swingvision_import/`, which only ever take an injected client. `scripts/import_match.py` is the CLI entry point that wires this together (`ingest()`, optional `--suggest`); `webapp/` (below) is a second front door onto the same pipeline. Three real bugs the live API surfaced that no synthetic test caught, now fixed: `claude-sonnet-5` rejects the `temperature` parameter outright; `response.content[0]` is unreliably a `ThinkingBlock` rather than text (extended thinking is on by default) — `ai.client.extract_text()` finds the first actual text block instead of assuming position 0; and despite every prompt in this codebase saying "no markdown fences," a response sometimes comes back wrapped in ` ```json ... ``` ` anyway — `ai.client.strip_markdown_fence()` strips it before `json.loads()`, shared by every JSON-parsing call site (`ai/client.py`'s own `call_specialist`, `review_assist.py`, `review_resolve.py` below).

**Human review answers, parsed but never auto-applied** (`review_resolve.py`, invoked via `pipeline.resolve()`): a different trust relationship than `review_assist.py`'s independent suggestions above — here the human has already reviewed the point and written their own plain-language conclusion into `PointRecord.review_answer` (e.g. "she was way out of position, that was a clean winner"), and Claude's only job is translating that into the point table's structured vocabulary (`point_end_type`/`point_won`/`net_approach`), landing in `resolved_*` fields — not re-judging the point itself. **Still never clears `needs_review`**: a separate, explicit `pipeline.apply_resolutions()` call is what actually copies `resolved_*` onto the real fields and clears the flag, so a parsing mistake gets one more human checkpoint before reaching `finalize()`. `resolve_point_answer()` also validates that the parsed `point_end_type`/`point_won` pair is internally consistent with `data/schema.sql`'s own `CHECK` constraint before returning — confirmed necessary against the live API, which once produced `point_end_type="ace"` paired with `point_won=false` (a real, invalid combination) despite explicit prompt guidance against it; that combination is now rejected at parse time (as a `ResolutionError`, degrading that one point gracefully) rather than surfacing as a confusing `IntegrityError` deep inside `finalize()`. CLI: `scripts/resolve_reviews.py <pending.json> --resolve` then `--apply`.

**Multi-part matches (a recording cut and resumed as separate files)** — `pipeline.ingest_multi_part(xlsx_paths, ...)` and `reconstruct.merge_shots()`: each file's own `Point` counter restarts from 1, so files can't just be concatenated — `merge_shots` shifts each subsequent file's point numbers to continue right after the previous file's highest, then the whole sequence is reconstructed once, so a set spanning the file boundary gets one correct combined score instead of two wrong partial ones. Requires every file to be the Shots-reconstruction case with a matching Settings host name. `MatchRecord.source_files` (a list) replaces `source_file` for these matches; `suggest()` checks it first and re-merges the same way before re-fetching shot context, so `source_point_number` (assigned from the merged sequence at ingest time) still resolves correctly. Confirmed against the real two-file match: the merge itself is mechanically correct (175 = 74 + 101 real points from the two files, no duplication or loss), but the *simulated* score still doesn't match the known true score (3 set-completions vs. the real 2) — concrete evidence that the per-point winner-classification heuristic accumulates real error over ~175 points, not a merge bug. **That reading is now in doubt:** on the 2026-08-21 export SwingVision's `Point` counter restarts at every serve attempt, so reconstruction scores each first-serve fault as its own point (24 phantom points there; merging fault + second serve moves the score from 7-5, 6-4, 2-1 to 7-6, 6-3 against the Sets sheet's 7-6, 6-2). The two-file match has not been re-checked, but the same unit error would inflate its score the same way - a structural bug to fix, not heuristic drift to live with. **Fixed in 5.8.0 for the single-file case:** `reconstruct.is_second_serve_attempt` folds a fault into the next serve attempt when it is the same server, same export part and same serving side (`RawShotRow.hit_zone`, the `Hit Zone` column) and the first serve was not in - or SwingVision itself labelled the next one `second_serve`. The label alone is not trusted: 17 of the 42 pairs on that export were both labelled `first_serve`. Without a serving side it falls back to the label plus a missed first serve. The merged point keeps the second attempt's `source_point_number` and the folded numbers are reported in `import_notes` (`ReconstructionResult.merged_fault_points`). Result there: 174 attempts -> 132 points, score 7-5, 6-2 against the real 7-6, 6-2. Six same-side pairs whose first serve was `In` (lets or tracking slips) are deliberately left as two points. Not yet built: taking game boundaries from server changes, which on that export give exactly the real 12 games + 9-point tiebreak + 8 games where the score simulation does not. Separately, the winner heuristic itself still isn't "fixed" by tuning it to fit the known answer — that would defeat the point of `needs_review`; it's exactly the case manual review exists for.

**Structured-data quality notes, informational and never blocking** (`quality_check.py`, composed into `MatchRecord.import_notes` by `ingest()`): three checks, all pure Python, no video, no API calls — reconstructed set score vs. the `Sets` sheet's own summary row (this alone would have surfaced the known 6-4-vs-actual-5-3 discrepancy immediately), serve-order vs. optional user-supplied ground truth (`first_server_by_set`, from the intake UI below — a mismatch implies host/guest may be reversed for that set), and self-reported identity vs. the `Settings` sheet's host name (`tracked_identity`). Unlike `needs_review`, `import_notes` never blocks `finalize()` — it's for the reviewer's awareness, alongside the gap/exclusion counts from `reconstruct.py` above.

## Web app: the Rally AI dashboard (React SPA) + JSON API

`webapp/` is a local Flask app with two responsibilities, kept deliberately separate:

- **`webapp/api.py`** — a `/api/*` JSON Blueprint that's the real front door onto every pipeline (`SwingVisionImportPipeline`, `stats.queries`, `ai.journal`) for the SPA below. No parallel business logic — every route is a thin wrapper.
- **`frontend/`** — a Vite + React + TypeScript + Tailwind + Recharts + `motion` single-page app (`npm install && npm run build` once; `webapp/app.py` serves the built `frontend/dist/` at `/`). Four tabs:
  - **Overview** — career stat tiles + highlights (`GET /api/overview`), and the Load Data flow: `POST /api/import` (unchanged `ingest()` fields) stages a match, then a **browser review modal** walks every `needs_review` point (`GET /api/pending/<file>`, optional `POST .../suggest` for Claude's opt-in shot-context suggestions, `POST .../confirm-point` per point) — this is what closes the "in-browser review UI" gap earlier versions left as CLI-only (`scripts/resolve_reviews.py` still works too, unchanged). Only once every flag is cleared does `POST .../finalize` become available; a tennis-ball progress animation (client-side, timed to the real request) plays during that call, then the real `match_id` is shown.
  - **Journal** — one sticky note per match (`match.pros/cons/notes`, no schema change — `PUT /api/matches/<id>/journal`), plus a Mouratoglou-style single-voice AI coach reply (`POST /api/matches/<id>/coach`, `ai/journal.py`) grounded in that match's stats and the journal text — an explicit, money-spending action the user triggers, cached like every other AI output (`ai/journal_feedback/<id>.json`, gitignored).
  - **Statistics** — Recharts trend/breakdown views over `stats.queries.all_match_stats`/`match_stats`, career or per-match.
  - **Film Review** — a minimal per-match video gallery (`GET /api/matches/<id>/media`, served via a `/media/<path:filename>` static route) — no clipping/tagging.
- **Multi-part uploads pair by filename** (`webapp/uploads.py`: `pair_uploads`, `save_paired_videos`). The exports field takes one file or many; **two or more means one interrupted recording**, so the route calls `pipeline.ingest_multi_part()` instead of `ingest()` and the files are merged into a single continuous reconstruction rather than staged as separate matches. The filename does two jobs there: (1) **play order** comes from a natural sort of the sanitized stems, since browser file order is arbitrary and `ingest_multi_part` can't recover a wrong order on its own (`part2` sorts before `part10`); (2) **footage is matched to the export sharing its stem**, case- and extension-insensitive (`set2.xlsx` <-> `set2.MP4`), because the two files come off different devices. Matched clips are saved as `partNN__<name>` so Film Review's plain `sorted()` listing plays them back in recorded order; anything matching no export is still saved, as `unpaired__<name>` (sorting after `part*`), never dropped. A **single** export is the trivial case - it is the whole match, so every clip belongs to it, filenames need not agree, and nothing is renamed. Mismatches are **informational, never blocking**, same as `import_notes`: they come back as `upload_notes` and are shown alongside the reconstruction's own notes. `frontend/src/components/PartPairing.tsx` previews the same pairing client-side *before* upload, so a mismatched name is caught while it's still one rename away from being fixed; the server's own answer (`parts`/`upload_notes` in the response) is the truth.
- **Staged exports are archived, footage is not** (`pipeline.archive_sources`, called by the import route once staging succeeds). The uploaded `.xlsx` copies in `data/uploads/` are packed into one `<match>_exports.zip` and the loose files deleted; the record's `source_archive` then points at the zip and `source_file(s)` hold *member names*. Measured, not assumed: a SwingVision `.xlsx` is an OOXML zip whose parts are stored with little compression, so deflating it again saves **~41%** on a realistic 26KB export. **Footage is deliberately excluded** — H.264/H.265 is already entropy-coded (measured at **-0.0%**, i.e. marginally *larger*), and zipping it would also break Film Review, which streams the file straight off disk through a `<video>` tag. Real video savings would need transcoding (lossy, `ffmpeg`), which is a different operation and not done here. `archive_sources` is **not** called by `ingest()` itself: the CLI path is handed the user's own file and must never delete it, so only callers that own their copies (the web app) opt in. It is idempotent, and unlinks originals only after the archive is closed and complete, so a failure part-way leaves everything intact. **`swingvision_import/sources.py`** is the one place that knows where a record's exports actually live (loose paths vs. archive members) — both re-parse consumers, `pipeline.shots_by_point` and `shot_map.embeddings._match_shots`, go through it, replacing the duplicated copy the latter's docstring used to apologise for.
- **The reviewer's own note** (`MatchRecord.reviewer_note`, the intake form's "anything odd about this import" field): free text the uploader writes at upload time about what the reconstruction can't see — most often why there is more than one export ("part 2 restarts mid-game"). Staged-JSON only, never a database column, exactly like `import_notes`. It's folded into `review_assist.py`'s per-point prompt as **background, explicitly not as an answer**, and echoed back in the browser review modal while the same points are being confirmed. It never resolves a flag.
- **Per-point suggestions run concurrently** (`pipeline.suggest`, `ImportConfig.suggestion_workers`, default 8): one Claude call per flagged point used to run serially, so a 175-point reconstruction meant ~175 sequential calls. Each call is independent and stateless (one point's own shots in, one classification out), making this the same sanctioned `ThreadPoolExecutor` case as `ai/generate.py`'s three specialists — concurrency changes only how long the batch takes. Results attach through an explicit `future -> point` map, never completion order, and a point that fails still fails alone. Two correctness details that come with it: transient failures (rate limit, connection, 5xx — which concurrency itself provokes) retry with backoff via `SuggestionConfig.max_attempts`, while malformed responses and 4xx deliberately don't; and points the reviewer has already confirmed are skipped, so re-running after a partial review neither pays nor re-annotates settled points.
- **Footage verification, the second independent source** (`swingvision_import/footage.py`, `pipeline.verify_footage`, `POST`/`GET /api/pending/<file>/footage`). Every reconstructed point is a guess from shot geometry, so this looks at the video and judges the same point again - and **a flag clears only when both sources agree**, which is the same "never one auto-tagger alone" rule that stops `suggest()` resolving anything. Three things make the result trustworthy rather than merely confident-sounding: (1) **Independence** - the vision prompt gets who served and which end each player is at, and *never* the recorded outcome; a test asserts structurally that neither `judge_point` nor `_prompt` can even see the point. (2) **Alignment** - `Video Time` indexes the **full-length recording** (confirmed on a real export: Settings start + video_time equals the shot's wall clock with zero drift over 180 points), so `check_alignment()` refuses any video too short to contain the recorded times, and each verdict independently reports the server it saw - a mismatch marks the point inconclusive instead of trusted, with a run-level warning when mismatches are widespread. (3) **Vocabulary** - `point_end_type` is from the tracked player's side using the buckets `reconstruct.py` actually assigns (an opponent's double fault is `return_winner`, an ace against us is `return_error`, and reconstruction never emits `forced_error`), or nothing could ever agree. Agreement also requires high confidence, self-consistency, and no contradicted net approach; disagreements and unclear readings stay flagged with the verdict attached as context (`PointRecord.footage_check`), and `confirmed_by` records whether a flag was cleared by a `human` or by `footage`. Opt-in and money-spending like `suggest()`: one vision call per flagged point, concurrent via the same sanctioned `ThreadPoolExecutor` case, with the estimate shown in the UI **before** anything runs (~$23 for 180 points on `claude-opus-5` at 1280x720 frames) and real billed cost reported after. Runs on a background thread tracked by `webapp/jobs.py` - deliberately process-local, since each verdict is written into the pending JSON as the run goes, so a lost job costs progress reporting, never results.
- **The recording's clock is measured, not assumed** (`footage.measure_clock_offset`, `offset_from_audio`, `shift_window`; `verify_footage(clock_offset=...)`). `Video Time` matching the wall clock does **not** mean it matches the video file: on the first real full recording the video ran **1.99s behind** the sheet, constant across all six sixths of 95 minutes, so the finish window ended before the rally did and all 10 sampled verdicts were inconclusive. Ball strikes are sharp sounds, so sliding the sheet's shot times along the audio's onset envelope gives one clear peak (9-13 standard deviations there). It runs before any API call, per part, full-length footage only; an offset under 0.25s is ignored, an unclear peak leaves the sheet's times alone and adds a run note. It is skipped when a test injects `frame_source` without `clock_offset`. With it, a second 10-point sample read the server correctly 10/10 and matched the sheet's winner on 6 of 9 readable points - all at medium or low confidence, so the high-confidence agreement rule cleared nothing. **Known quirk:** `verify_footage` saves to the record's own `pending_name`, not to the `json_path` it was given, so running it on a copy writes the verdicts to the original.
- **The ball's path is drawn, not sampled** (`footage.compose_ball_path`, `ball_path_image`, `ball_path_caption`; `FootageConfig.ball_path*`). Eight stills across three seconds usually miss the bounce, and the first real verdicts said so. The last frame sent for each point is now a composite: the frame at 0.3s before the final shot with everything that moved over the next 3.3s painted on, blue to red by time. Movement is three-frame differencing on the green channel (marks a thing where it is, no ghost where it was); ball-sized movement is painted solid and player-sized movement only tints, told apart by counting moving pixels per 40px block. It is explained to the judge by the frame's own `caption`, not by `_prompt`, so the judge's parameter allowlist is unchanged, and the caption is tested to name no outcome. It never raises - a point it cannot be built for is judged from the stills. **Measured, 10 points, $1.82:** readable 10 of 10, winner matches the sheet 7 of 10, confidence 6 medium / 4 low / 0 high. So it improves the reading and does **not** reach the high-confidence bar; it costs ~13s of decoding and ~4,000 output tokens a point (`estimated_output_tokens` raised to match). The stills-only and with-path readings of the same point agree on 7 of 10 and all three sources agree on 5 - evidence for a corroboration rule, which is the user's decision (design doc section 3) and is **not built**.
- **Two readings can clear a flag together** (`footage.corroborate`, `wants_second_reading`, `_reading`; `FootageConfig.corroborate`, `corroboration_confidence`; `FootageRunSummary.corroborated` / `second_readings`; `footage_check["second_reading"]`). **This changed the rule above, by the user's explicit decision on 2026-11-24:** "agreement requires high confidence" now holds only for a reading standing alone (`compare`). When the first reading - stills plus ball path - is medium, `check_full` takes a second from the stills alone (the frames with no `caption`), and the flag clears when both readings and the sheet agree and neither is below `corroboration_confidence` (default `medium`; `low` is the prompt's word for a guess). Each reading still has to pass every other check. Two readings telling the same story against the sheet give `disagrees`; the point stays flagged and nothing is overwritten - the sheet is **not** overridden by footage, which is the further step in design doc section 3 and is not built. No second reading is taken when the first is high (decides alone), below the floor, unreadable, failed an alignment check, or when there is no ball-path frame to leave out (so tests injecting a bare `frame_source` see one call per point). Full-length footage only. **Known limit, stated on purpose:** same model, same video - a shared blind spot fools both readings; the sheet is the independent third. **Measured** by replaying stored readings of the 10 sample points: 2 agree, 1 disagrees, 7 inconclusive at the medium floor (5 / 2 / 3 at `low`). The review modal does not yet show the second reading.
- **A serve's Result cell is outranked by what happened next** (`reconstruct.reconstruct_point`). A serve followed by a second serve was a fault; a serve its own server hit another shot behind was in; and a double fault is lost by the server even if the fault was hit back. Before this, 5.8.0's merge produced `double_fault` with `point_won=True` on two real points, a pair the `point` table's CHECK rejects.
- **`GET /api/pending` lists staged matches** so a review can be resumed. Before this, the review modal was reachable only in the browser session that staged the match - a closed tab meant re-uploading the whole thing, footage included, to finish reviewing it.
- **Correction (2026-11-23) to the next bullet, measured on the 2026-08-21 match and not yet built into the pipeline** - see [docs/footage-first-design.md](docs/footage-first-design.md) section 0. Two different exports exist: an overlay version (shot label burned in; what the next bullet measured) and a raw rallies-only version (1080x1080, no overlay; what is on disk). On the raw version a frame-difference scan finds 124 clips against the user's stated 123 rallies, and aligning clips to the sheet **by order and duration** places 117 of 124 within one second (51-57 with the order shuffled) - so "order-based matching is unsafe" and "the full-length recording is required" no longer hold for locating a rally, though loose matches still need a per-clip margin. What the video leaves out is first-serve faults (23 of 28 one-shot points) and about half the two-shot points, **not** "every ace, double fault, service winner and return error"; the ~45% / ~70% figures are superseded. The 5.6.0 retrieval prompt matched stroke/spin/speed labels, which raw footage does not carry - the likely reason its sample returned only `low`.
- **The uploader's rally count** (`MatchRecord.footage_rally_count`, intake field "Total rallies in the match (from the footage)", `--footage-rally-count`, phone metadata; staged JSON only, validated by `records.parse_footage_rally_count` for all three front doors). Carried on `FootageRunSummary` and the footage status API so it is shown beside `points_played` everywhere, and cross-checked by `quality_check.check_footage_rally_count`, whose note states the coverage ceiling **without naming a cause** - the cause was asserted once and turned out wrong.
- **Import notes are shown inside the review modal**, not only once review is finished, and a resumed review loads them from the staged file. Intake numbers (ratings, rally count) are validated **before** any upload is written, so a form error never strands files or stages a match that cannot be finalized.
- **The footage check for rallies-only video cannot be started from the browser.** `_footage_status` always runs `check_alignment`, and `startFootageCheck` sends no body, so `source="condensed_rallies"` is reachable only through the API - despite `source` being in `_FOOTAGE_OVERRIDES`. Also open: the status endpoint re-parses the export on every 2s poll during a run, and `footage.py` (87%) and `pipeline.py` (96%) are below the 100% coverage bar.
- **SwingVision's condensed export cannot be used for footage checks** - now measured rather than inferred, in [docs/condensed-export.md](docs/condensed-export.md). Its rallies-only video is roughly a fifth the length of the recording its timestamps refer to and carries no timestamp map. Reconstructing position arithmetically (rally spans concatenated plus a fitted padding) lands within **+/-5 points** - a usable search window, not a way to grab the right rally. The blocker is worse than drift: the export keeps all *rallies*, which is not all points. Counting serves by overlay text width (a free, deterministic check - "Serve" is 61px where "Forehand"/"Backhand" are 100-107px) finds **71 serve displays against the sheet's 174**, and the median gap between them (16.0s) fits the **>= 4 shots** subset - roughly **80 of 176 points, ~45%**. It is a biased sample, not a shortened one: **every ace, double fault, service winner and return error is absent**, because none of them is a rally. Order-based matching is therefore unsafe, and no alignment accuracy fixes it - the points are not in the file. There is no burned-in score or rally number to index by, and the label's colour encodes neither player nor result, so nothing may be built on it. The full-length recording is required, and the guard says so by name. **Every video supplied so far has been the condensed one** - including the two 2026-08-18 files previously taken for full recordings - so the footage check has never yet run on real data.
- **The tracked player is identified by appearance, not by court end** (`MatchRecord.player_appearance`, intake field "What you were wearing"). Ends swap at changeovers, so `NEAR`/`FAR` alone cannot say which player is the user. A positive sighting at the end the sheet did not expect marks the point **inconclusive**, exactly as a server mismatch does. It says which player to look at, never what happened to them, so it cannot leak the outcome - `test_the_judge_is_never_given_the_recorded_outcome` asserts the prompt's parameter allowlist exactly, so anything new reaching the judge has to be argued for there.
- **`GET /report/<match_id>` is unchanged** and stays outside the SPA on purpose — the standalone, self-contained downloadable report (`reports.render.render_match_report`), still readable with no server running. Never spends API money: reads whatever `ai/reports/<match_id>.json` is already cached, never constructs a client.
- **`stats.queries.all_match_stats(db_path, match_ids)`** replaces the old sequential per-match loop with a **`ThreadPoolExecutor`**-backed concurrent fetch (each worker opens its own short-lived SQLite connection — a single `Connection` isn't safe to share across threads) — the second sanctioned use of `ThreadPoolExecutor` in this codebase alongside `ai/generate.py`'s, both independent/stateless-read cases. `career_stats_from_matches` is the pure aggregation step over the result, unit-testable with no DB or threading involved.
- **The browser review UI's direct-confirm path** (`swingvision_import.review.confirm_point`, wrapped by `pipeline.confirm_point`) is new: the human picks a point's real `point_end_type`/`net_approach` straight from UI controls (no Claude call required for the common case) and `point_won` is derived client-side from `WINNING_END_TYPES` so an inconsistent pair can't even be submitted — enforced again server-side via the same `records.VALID_END_TYPES`/`WINNING_END_TYPES`/`LOSING_END_TYPES` constants `review_resolve.py`'s AI-parsing path already used (promoted to `records.py`, one source of truth instead of two copies). Still never bypasses the gate: `needs_review` only clears per-point, and `finalize()` still refuses a match with any flag remaining.

### Design system & interaction primitives

`frontend/src/index.css` is the whole visual system, modelled on [proteusbio.ai](https://proteusbio.ai/) - its palette, type stack and layout conventions were read off the live site's own CSS, not approximated. Warm paper (`#F4F1EA` ground, `#FBF8F0` raised, `#EFEADD` sunk), near-black ink (`#0B1515`), warm hairlines (`#E7DECB`/`#DAD3C4`), and exactly three accents each with one job: terracotta `#BC5B45` = action/live, blue `#2E5FA8` = data series, teal `#1E9E8A` = good/won (plus `#B65440` clay for lost). Type is Fraunces (display, variable `opsz`), Geist (text), Geist Mono (eyebrows and every figure) - loaded from Google Fonts in `frontend/index.html`. Component classes (`.wrap .display .h2 .h3 .lede .eyebrow .num .panel .panel-sunk .field .btn .link`) carry the system; depth comes from a hairline and a 2px lift, never shadow or blur - which is why `GlassCard` was deleted rather than restyled, since translucent-blur-over-dark means nothing on a light paper ground.

Reusable interaction primitives, all in `frontend/src/components/`, every one of which **stands down under `prefers-reduced-motion`** (returning a plain wrapper, or - for the CSS-driven ones - stopped by index.css's own reduced-motion block):

- `Reveal` - scroll-triggered entrance, `once: true` (a reveal that re-fires reads as a bug when scrolling back up).
- `SplitText` - word-by-word headline entrance. Split by word, not character, so selection and screen readers survive; the full string stays on an `aria-label`. Its clip box is padded and negatively margined because a `line-height` under 1 otherwise cuts descenders. **The gap between words is a real space, never a margin** - a margin renders the gap correctly while the text itself reads `Everymatchyouplay`, which is what selecting and copying a headline produced until the behaviour suite caught it.
- `Magnetic` - primary actions pull toward the cursor. Used sparingly on purpose; everything doing this at once is soup.
- `Cursor` - a trailing ring plus dot that swells over anything clickable. Never hides the real cursor, and mounts only for `(pointer: fine)`.
- `Counter` - counts a figure up when it scrolls into view. Only for figures where the intermediate values mean something - never ids, dates, or score lines.
- `Panel` - the one card surface, optionally cursor-tilted (max 5 degrees) and spotlit; the highlight gradient lives in CSS and JS only writes `--mx`/`--my`.
- `Marquee` - a CSS-keyframe ticker, deliberately not a JS animation, so `:hover` can pause it with `animation-play-state`.
- `Dropzone` - drag-and-drop over a genuine `<input type="file">`; dropped files are assigned onto `input.files`, so Overview's `new FormData(form)` submit is unchanged. Deliberately **not** `required`: a `display:none` required control makes Chrome abort submit with "not focusable", so Overview validates the .xlsx in its own handler, and resetting remounts the form (`formKey`) to clear the dropzone's filename state.

`reports/`'s standalone `report.html` is untouched by this and still uses `reports/palette.py`'s dataviz-skill palette - it's a separately-generated downloadable file the SPA does not link to, and its hexes are lifted verbatim from a validated reference palette. The two surfaces no longer match, by choice.

Uploaded files are sanitized via werkzeug's `secure_filename` before touching disk (`data/uploads/`, `data/media/`, both gitignored) so a hostile upload filename can't path-traverse out of them. Run with `python webapp/app.py` (binds to `127.0.0.1` only, per Flask's own default — never meant to be exposed beyond localhost); rebuild the frontend (`cd frontend && npm run build`) after editing anything under `frontend/src/`.

## Derived stats

`src/stats/` computes everything in `docs/stat-definitions.md` by reading `data/schema.sql` back out — nothing derived is stored redundantly, matching the schema's own design intent.

- **`queries.py`** has one function per stat category (`serving_stats`, `receiving_stats`, `point_outcome_stats`, `net_stats`, `clutch_stats`), each taking `(conn, match_id, set_id=None)` — `set_id=None` aggregates the whole match, a given `set_id` scopes to one set. `match_stats(conn, match_id)` assembles the full `MatchStats` bundle used by both the AI coach and the HTML report. Game-level scope (the third tier in `stat-definitions.md`) isn't implemented yet — adding it is a parameter, not a rewrite.
- **`scoring.py`** derives break-point and deuce-point status by replaying each game's points in order under a running point tally — neither is a stored column, both are properties of where a point falls in its game's score. **Tiebreak games are excluded** from break/deuce detection entirely (a tiebreak's server rotates within the game itself, so "break point" doesn't map onto that scoring the same way) and from service/return game-holding counts (same reason — a single game-level `is_serving` value isn't well-defined for a tiebreak under this schema).
- Every percentage/ratio field returns `0.0` when its denominator is 0, never `None` or a raised error — keeps every stat field a plain `float`, renderable without `Optional`-handling downstream. This means "0%" and "no data" aren't distinguished; revisit only if that turns out to matter.
- `DC` (deuces converted) follows the same convention as `BPC` (break points converted): "point_won = TRUE" on a deuce/break point, not the stricter "and the game was won" reading `stat-definitions.md`'s wording could also support — chosen for consistency between the two, not because the wording was unambiguous.

## AI coaching engine

`ai/` (a standalone top-level package, not nested under `src/` — its own `pythonpath` entry in `pyproject.toml`) generates one `CoachingReport` per match: strategy insights, drill recommendations, and fitness/conditioning notes.

- **Three parallel, stateless Claude Sonnet 5 calls** (`generate.py`, via `ThreadPoolExecutor`) — strategy / drills / fitness — each sees the same deterministically-built `CoachContext` (`context.py`, pure data assembly from `MatchStats`, no LLM). No tool-using subagents, no 4th "synthesis" call: this is the one place in the codebase `ThreadPoolExecutor` is actually used, matching the specific carve-out named below.
- **"Improvement plan" is a derived `@property`** on `CoachingReport` (`records.py`) — every item from strategy/drills/fitness combined, sorted by `priority`. Never generated or stored separately, so it can't drift out of sync with the three specialists' actual output.
- **Every item carries a `SupportingStat`** (which stat, its value, optionally a comparison) — this is what makes "specific to this match's stats, not generic boilerplate" (the UAT checklist item below) something a test can assert on rather than eyeball.
- **The Anthropic client is always injected**, never constructed inside `ai/` itself (`client.py`'s `call_specialist`, `pipeline.py`'s `generate`) — so tests never touch the real API or spend real money. `tests/ai/conftest.py`'s `FakeAnthropicClient` is the standard fake to reuse.
- **Incremental state tracking lives on the filesystem**, same pattern as SwingVision's pending JSON: `pipeline.AICoachPipeline.generate()` skips calling the API and loads the cached report if `ai/reports/<match_id>.json` already exists, unless `force=True`. `ai/reports/` is gitignored — personal AI output, not code.
- **Optional shot-pattern enrichment, no schema change:** `generate()` best-effort looks up the match's original staged JSON via `swingvision_import.review.find_pending_path(date, opponent, pending_dir)` (matched by the `date`/`opponent` already on the `match` row — no new column needed to link SQL back to staging JSON) and folds its `shot_pattern_summary` (rally-length aggregates computed once at `ingest()` time in `reconstruct.py`, from the reconstruction path only) into `CoachContext.stats` when present. Purely additive — a deleted pending file, a direct-parse match with no raw shots to summarize, or a corrupt file all degrade silently to today's stats-only behavior; this is the only place `ai/` depends on `swingvision_import` at all, and only on its small, data-only `review.py`, not the parser/reconstruction modules.
- A specialist call that fails — either the API call itself (`anthropic.APIError`: auth, rate limit, network) or a response that parses but doesn't match the schema — raises `SpecialistError` either way, and `generate.py` catches it per-specialist: that section comes back empty rather than taking down the whole report. Both failure modes are handled identically on purpose, since the point is graceful degradation, not distinguishing *why* a specialist failed.

## Report generation

`reports/` (also standalone top-level) is the one piece that consumes *both* `stats` and `ai` output: **one self-contained, downloadable `report.html` per match** (stats breakdown + AI coaching insights together). `render_history_report` produces a second, separate cross-match trend page from the same building blocks. Both are now also reused live inside `webapp/`'s Results tab (below) rather than only existing as separately-generated static files — `render_match_report`/`render_history_report` (the string-returning functions, not the `_to_file` variants) are the actual shared surface both the CLI and the webapp render from.

- **Charts are hand-rolled inline SVG+CSS+JS** (`charts.py`), following the `dataviz` skill's method (pick the form → assign color by its job → mark specs → hover layer) instead of a plotting library — matplotlib was explicitly ruled out (static, no real interactivity, and its default look was the thing being avoided). Every hex value in `palette.py` is lifted verbatim from the skill's validated reference palette, never re-derived or eyeballed.
- **Six chart primitives** cover the outline: `bar_chart` (sequential hue — magnitude, not identity), `stacked_bar_chart` (2-category only: serve in/out), `line_chart` (single series, per-point hover rather than a continuous crosshair — a deliberate v1 simplification), `stat_tile`, `meter`, and `status_strip` (win/loss — uses the fixed **status** palette, not categorical, since win/loss is a state). A genuine multi-series `line_chart` variant (for the combined hold%/return% trend from the original ideation) doesn't exist yet — cut for v1 rather than rushed, with no real multi-match data yet to validate it against anyway.
- **Every label is free text from the database or the AI** (opponent names, `pros`/`cons`, observation/recommendation text) — `charts.py` HTML-escapes anything going into an SVG attribute and reads it back via `.dataset`/sets it via `.textContent` in the emitted JS, never `innerHTML`. Jinja's `autoescape` is on in `render.py`; only pre-built chart fragments (already escaped internally) are marked `| safe`, never raw user or AI text. A chart's DOM id is also JSON-escaped before being spliced into its own `<script>` block, not just HTML-escaped for the attribute — the two contexts need different escaping and only satisfying one isn't enough.
- **`config.py`'s `ReportConfig`** supplies the default output location (`reports/output/`, gitignored) for both `render_match_report_to_file` and `render_history_report_to_file` — an explicit `output_path` always wins if given, the config only fills in when it's omitted.
- **`scripts/generate_report.py`** is the CLI entry point: `python scripts/generate_report.py <match_id>` (requires the match already `finalize()`d into SQL — the last pipeline step, after ingest → review → resolve/suggest → finalize) generates/loads the cached AI coaching report and renders the match report together; `--no-ai` skips the API call for a stats-only render; `--history` renders the cross-match trend report instead of one match's.

## Testing

**Backend:** pytest for unit tests. Run with coverage (`pytest --cov`) — treat coverage gaps as a signal to look for untested *or redundant* paths, not just a number to push up. Run via `pytest --cov=swingvision_import --cov=stats --cov=ai --cov=reports --cov-report=term-missing` from the repo root (config in `pyproject.toml` puts `src` **and the repo root** on `sys.path` — `ai`/`reports` are top-level, `stats` is under `src/` — and points `testpaths` at `tests/`, which mirrors each package 1:1: `tests/swingvision_import/`, `tests/stats/`, `tests/ai/`, `tests/reports/`, `tests/webapp/`). The AI coach's tests never call the real Anthropic API — every one injects `tests/ai/conftest.py`'s `FakeAnthropicClient`; `tests/webapp/`'s Flask test client does the same via `create_app()`'s injected `ImportConfig`/`WebAppConfig`. `scripts/` and `webapp/` are entry-point code (like `scripts/import_match.py`'s CLI and `webapp/app.py`'s routes) and aren't held to the 100%-coverage bar the four `--cov=`-tracked packages are — still tested, just not coverage-gated. **Behaviour checks** (`scripts/e2e_check.py`, `e2e/harness.py`, `e2e/dashboard.json`) are the frontend's automated suite, and deliberately not part of `pytest` — they need a built frontend and a live server, so they are their own step: `python scripts/e2e_check.py`. The harness drives the real dashboard with Playwright across all four tabs at **desktop and phone width**, asserting on console errors, uncaught exceptions, failed requests, selectors, rendered text and horizontal overflow, and writes screenshots plus a JSON report to `e2e/output/` (gitignored). It exists because unit tests and behaviour are close to independent: the bug that prompted it — every masthead rendering as `Everymatchyouplay,kepthonestly.` because `SplitText`'s word gap was a CSS margin rather than real whitespace, so selecting and copying a headline produced run-together words — passed `tsc`, `ruff` and all 344 backend tests. **`e2e_check.py` refuses to run against a stale build**: it rebuilds by default, and compares `frontend/src` modification times against `frontend/dist/` (plus the served bundle hash against the built one), because a behaviour run against code you already changed is worse than no run — it reports confidently on something that is not under test. `tsc -b` via `npm run build` remains the type check.

**Frontend (UAT):** an objective checklist tied to the user-facing features in the README, not implementation details:

- [ ] Match creation captures date, opponent, result, energy/mental ratings
- [ ] Games can be logged one at a time within a set, points logged sequentially within a game
- [ ] Derived stats (FS%, BP%, W/UE ratio, etc.) recompute and display correctly once a match is fully logged
- [ ] 3 pros / 3 cons can be entered and are attached to the correct match
- [ ] AI coach output is specific to the logged match's stats + pros/cons, not generic boilerplate
- [ ] Dashboard charts reflect trends across multiple matches, not just the most recent one
- [ ] Match history lists all past matches, and opening one shows its full stat breakdown
- [ ] Data persists across a page reload / new session
- [ ] Manual-review flags (winner/UE/FE tags, net approach) surface in the UI for the user to confirm before a match's stats are treated as final

## Code conventions

Backend: SQL database (SQLite) for storage, Python for stat aggregation, the SwingVision import pipeline, the AI coach (`anthropic` SDK), and report generation (`jinja2`). `reports/`'s generated HTML is the read/output surface, reused live inside `webapp/` (Flask) — the one live, interactive surface, now covering both intake and a finalized-matches results dashboard. The in-browser review UI for resolving `needs_review` flags is Overview's review modal; the CLI/hand-edit-JSON route still works.

- **Dataclass-based configuration** — config objects (AI prompt settings, SwingVision import settings, stat-calc parameters) as `@dataclass`, not raw dicts.
- **Pipeline classes with incremental state tracking** — SwingVision import and the AI coach are structured as pipeline classes (`SwingVisionImportPipeline`, `AICoachPipeline`) that track what's already been processed via the filesystem (an existing pending/report file means skip, not reprocess) — never reprocess or duplicate by default.
- **Per-module logging** — `logging.getLogger(__name__)` per module, not a shared root logger. Library modules never configure handlers themselves; `logging_config.configure_logging()` (repo root) is the one place that does, meant to be called once by whatever entry point exists — a script, eventually a CLI. Without calling it, none of the per-module `logger.info(...)` calls anywhere in the codebase actually go anywhere.
- **Docstrings** — every module, class, and function gets a Google-style docstring (`Args:` / `Returns:`, plus `Raises:` and `Attributes:` where relevant). This is initial architecture and will keep shifting, so the docstrings are how the *current* contract of each piece stays legible as things move, not a one-time formality.
- **Ruff**: rules `E, F, I, W`, 100-char line limit.
- **Parallel processing via `ThreadPoolExecutor`** — two sanctioned places, both independent/stateless-read-or-call cases: `ai/generate.py`'s three concurrent coaching-specialist calls, and `stats.queries.all_match_stats`'s concurrent per-match SQLite reads (each worker opens its own connection) backing the webapp's Overview/Statistics tabs. Not a blanket convention — day-to-day backend work (one user, one match at a time) still doesn't need it anywhere else.

**Given a second look, not adopted for now** (flagged here rather than silently dropped, in case a future feature changes this):

- **Sparse matrix handling** — Rally AI's data is small and dense (per-point flags, per-match stats), not high-dimensional/sparse. No current feature needs it; revisit only if something like large-scale cross-match feature vectors gets built.
